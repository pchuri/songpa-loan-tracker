# iPhone Scriptable 위젯

아이폰의 [Scriptable](https://scriptable.app) 앱으로 송파구립도서관 대출·상호대차 현황을 보는 스크립트입니다.
서버 없이 아이폰이 도서관 홈페이지에 직접 로그인해서 조회합니다.

- **홈 화면 위젯**: 반납이 가까운 책 4권과 픽업할 책 알림
- **전체 화면**: 위젯을 누르면 계정별 카드 목록이 열립니다
  - 위쪽 이름 탭에 `이름 전체권수 (상호대차권수)` 표시 (상호대차 권수는 빨간색)
  - 대출중(반납일·D-Day), 픽업필요(도서관 도착), 이동중(상호대차 배송 중)을 한 표에 표시
- 여러 계정 지원 (가족 계정을 한 번에 조회)
- 라이트/다크 모드: 위젯과 전체 화면 모두 아이폰 화면 모드 설정(자동 전환 포함)을 따라갑니다

## 파일

| 파일 | 역할 |
|---|---|
| `songpa-loan-tracker.js` | 메인 스크립트 (위젯 + 전체 화면) |
| `songpa-accounts.js` | 계정 설정. 아이디·비밀번호·(선택) 회원번호를 입력받아 iOS 키체인에 저장 |
| `songpa-identity-check.js` | **생성본** 본인 확인 진단 스크립트 (아래 "본인 확인 진단"). 저장소에서 `node scripts/build-scriptable-identity-check.mjs`로 만듭니다. 손으로 고치지 않습니다 |

계정 정보는 코드에 적지 않습니다. `songpa-accounts.js`가 입력받은 값을 그 기기의 키체인(`SPLIB_ACCOUNTS`)에만 저장하고,
메인 스크립트는 키체인에서 읽어 도서관 홈페이지(splib.or.kr) 로그인에만 사용합니다.
메인 스크립트가 서버에서 확인한 회원번호는 계정 목록과 **별도의** 키체인 항목(`SPLIB_VERIFIED_MEMBERS_V1`)에 아이디·회원번호만 저장합니다 (비밀번호·쿠키 없음).
메인 스크립트는 `SPLIB_ACCOUNTS`를 절대 쓰지 않습니다.

## 설치

1. App Store에서 **Scriptable** 설치
2. Scriptable에서 `+`로 새 스크립트를 만들고 `songpa-accounts.js` 내용을 붙여넣기 → 실행(▶)
   - **계정 추가**로 이름(화면 표시용), 도서관 홈페이지 아이디, 비밀번호를 입력합니다. 계정마다 반복
   - **회원번호는 선택 항목**입니다. 비워 두면 첫 조회에서 아래 "서버 주체 증명"을 통과한 경우에만 회원번호를 별도 기록에 저장합니다.
     직접 넣으려면 회원증이나 도서관 홈페이지 마이페이지에서 **직접 확인한 값**을 넣으세요. 직접 넣은 값은 그대로 유지되고 대조에 쓰입니다
   - 홈페이지에 표시되는 회원 이름은 선택 항목입니다. 넣으면 이름도 함께 대조합니다 (아래 "회원 이름(선택 항목)" 참고)
3. 새 스크립트를 하나 더 만들고 `songpa-loan-tracker.js` 내용을 붙여넣기 → 실행해서 목록이 뜨는지 확인
4. 홈 화면 길게 누르기 → 위젯 추가 → Scriptable(중간 크기) → 위젯 편집에서 Script로 3번 스크립트 선택

스크립트 이름은 자유롭게 지어도 됩니다.

## 회원번호가 선택 항목으로 바뀜 (v1.2.6)

- v1.2의 "계정마다 회원번호 필수"를 없앴습니다. `{label, id, pw}`만 있는 예전 계정도 조회합니다. 기존에 저장한 계정 목록은 그대로 읽습니다.
- 자동 업데이트는 메인 스크립트(`songpa-loan-tracker.js`)만 바꿉니다. 아이디·비밀번호만으로 계정을 **추가**하거나 회원번호를 **고치려면**
  이 저장소의 `songpa-accounts.js`를 사용하세요. 메인 자동 업데이트는 설정 스크립트를 덮어쓰지 않습니다.
  예전 설정 스크립트로 저장한 계정 목록은 그대로 읽습니다. 자동으로 계정 목록을 고치거나 옮기지 않습니다.
- 회원번호가 없는 계정은 조회할 때마다 아래 "서버 주체 증명"을 하고, **처음 증명에 성공했을 때만** 그 응답의 회원번호를 별도 기록에 저장합니다.
  "첫 응답을 믿는(TOFU)" 방식이 아닙니다: 서버가 같은 세션에서 보여 준 로그인 아이디가 저장한 아이디와 **정확히** 같아야 하고,
  모든 목록 페이지와 마지막 증명까지 통과하고, 계정 간 충돌 검사도 통과해야 저장합니다. 이름은 근거로 쓰지 않습니다.
  이 검증은 해당 화면의 hidden `userId`가 서버 세션의 로그인 주체를 나타낸다는 전제에 의존합니다. 한 계정의 화면 구조를 관측했으며 서버 구현 자체를 감사한 것은 아닙니다.
- 직접 입력한 회원번호는 그대로 유지·우선하며 자동 기록으로 덮어쓰지 않습니다. 직접 입력한 값과 기록이 다르면 조회하지 않습니다.
  저장된 회원번호 값이 **형식이 틀리면** 오류로 보고, 기록·아이디만 확인으로 대신하지 않습니다.
- 이름·비밀번호만 고쳐도 저장된 회원번호·회원 이름은 그대로 유지됩니다. 수동 회원번호나 회원 이름을 지우려면 해당 칸에 `-`를 입력하세요.
  수동 회원번호를 지워도 별도 검증 기록은 유지하며, 다음 조회에서 서버 증명을 다시 하고 그 기록과 대조합니다.

## 본인 확인과 실패 처리

v1.1까지는 "다른 계정과 회원 이름이 같으면 세션 섞임"으로 판단해서, 동명이인은 잘못 지워지고 처음 잘못 받은 결과는 그대로 믿는 문제가 있었습니다.
v1.2는 계정마다 직접 입력한 회원번호를 기준으로 확인했고, 이 버전은 여기에 **서버 주체(로그인 아이디) 증명**을 더해 회원번호 없는 계정도 지원합니다.

- 조회 순서(계정마다): 일반 로그인 → **회원정보 확인 화면(주체 증명)** → 메인 화면 → 대출·상호대차 목록의 모든 페이지 → 메인 화면 재확인 → **회원정보 확인 화면 재증명**.
  처음 증명에서 정한 회원번호(직접 입력값·기록·첫 확인값 중 하나)를 그 실행에서만 쓰는 고정된 사본에 담아 이후 모든 페이지를 대조합니다. 계정 원본은 바꾸지 않습니다.

- 로그인 응답에서 **새로 받은 JSESSIONID**만 씁니다. 없거나, 여러 개거나, 형식이 이상하면 조회하지 않습니다.
  앱 공용 쿠키 저장소에 남은 예전 쿠키로 대신하지 않습니다.
- **로그인 요청의 익명 Cookie**: 로그인 요청에도 `Cookie: cookie=1`(JSESSIONID 없는 무해한 고정 값)을 직접 붙입니다.
  `Cookie`를 지정하지 않으면 공용 저장소가 이전 계정·이전 실행의 JSESSIONID를 로그인 요청에 붙일 수 있고,
  그러면 서버가 새 세션 대신 그 세션을 이어 쓸 수 있습니다. 빈 `Cookie` 값은 저장소 병합을 막지 못할 수 있어 비어 있지 않은 값을 씁니다.
  비어 있지 않은 직접 지정 `Cookie`가 저장소와 합쳐지지 않고 그대로 전송되는 것은 Mac Scriptable 합성 검증(로컬 서버)에서만 확인했습니다.
  실제 iPhone의 Scriptable과 실제 splib.or.kr 서버가 이 값을 어떻게 처리하는지(예: 알 수 없는 쿠키를 거부하는지)는 확인하지 못했습니다.
  이 헤더는 보조 수단일 뿐이며, 새 JSESSIONID 요구·페이지별 회원번호 확인·세션 교체/계정 간 충돌 시 숨김은 그대로 유지합니다.
- 리다이렉트는 따라가지 않습니다(`onRedirect`에서 `null` 반환). 로그인 응답은 상태 코드·이동 위치·주소·내용을 확인하고,
  이후 모든 요청에는 받은 쿠키를 `Cookie` 헤더로 직접 붙입니다.
- 회원번호는 로그인 직후, **목록의 모든 페이지(빈 페이지 포함)**, 조회가 끝난 뒤 다시 한 번 확인합니다.
  다르거나 둘 이상이거나 **목록 페이지에 회원번호가 없으면** 그 계정의 결과를 **전부** 숨깁니다.
- 로그인 뒤 응답이 `Set-Cookie`/응답 쿠키로 JSESSIONID를 바꾸거나 지우면(형식 오류·여러 개 포함) 본문의 회원번호가 맞아도 그 계정 결과를 모두 숨깁니다.
  같은 값이라도 삭제 속성이 붙으면 삭제로 봅니다. 쿠키마다 속성을 따로 읽고, `Max-Age`가 있으면 HTTP 규칙대로 `Expires`보다 우선합니다:
  `Max-Age`가 0 이하(`0`, `-1`)이거나 정수가 아니면 `Expires`가 미래여도 삭제, 양수면 `Expires`가 지났어도 유지입니다.
  `Max-Age`가 없으면 지난(또는 읽을 수 없는) `Expires`를 삭제로 봅니다. 응답에 쿠키가 없거나 같은 값(만료 아님)이면 정상입니다.
- **호환성 요구 (엄격해짐)**: 목록 페이지마다 페이지 어딘가(머리·옆·아래 영역 포함)에 아래 "회원번호를 읽는 화면 구조" 중 하나가 있어야 하고,
  페이지 전체에서 회원번호가 하나뿐이어야 합니다(목록 아래쪽에 다른 회원번호가 있어도 거부).
  앞뒤 메인 화면(index)의 회원번호가 같아도, 그 사이 목록 응답이 다른 회원의 것일 수 있어 그 페이지의 주인을 증명하지 못하기 때문입니다.
  실제 목록 화면에 회원번호가 없으면 모든 계정이 "N페이지: 화면에서 회원번호를 찾지 못했습니다"로 실패합니다.
  이때 회원 이름만으로 확인하도록 되돌리지 않습니다(이름은 신원이 아님). 파서를 실제 화면 구조에 맞춰 고쳐야 합니다.
- 한 번 실행하는 동안 두 계정에서 같은 회원번호가 보이면 **관련 계정 모두** 숨깁니다.
  같은 세션 ID라도 서로 다른 로그인 ID·회원번호를 초기/최종 서버 증명과 모든 목록 페이지에서 확인했고, 앞 계정 조회를 완전히 끝낸 뒤 다음 계정에 로그인했다면 각 결과를 표시합니다.
  이 순차 실행 예외는 내부 조회 루프가 만든 완료 기록에만 적용합니다. 실패·시간 초과·미완료 목록·다른 실행의 결과에는 적용하지 않습니다.
- 회원 이름은 신원으로 쓰지 않습니다. 같은 이름이라도 회원번호가 다르면 정상입니다.
- 화면에는 쿠키·회원번호·비밀번호를 표시하거나 로그로 남기지 않습니다.

### 회원번호를 읽는 화면 구조

아래 형태만 회원번호로 인정합니다.

1. **관측된 형태 (라벨 없음)**: `<div class="barcodeInfo">표시 이름<span>회원번호</span></div>`.
   앞쪽에 요소 없는 글자(표시 이름, 없어도 됨)가 오고, 직접 자식 요소는 `<span>` **하나뿐**이며, 그 뒤에는 공백만 있는 형태입니다.
   `회원번호 :` 같은 라벨은 없습니다. 앞쪽 글자는 회원 이름 대조에만 쓰고 회원번호·신원으로는 절대 쓰지 않습니다. 한 계정의 로그인 상태에서 Chrome으로 받은 원본 HTML을 한 번 읽어 확인한 구조이며
   (메인 화면·모바일 회원증·대출 목록 1페이지·상호대차 목록 1페이지에서 같은 구조, 같은 값), 실제 값은 저장소에 남기지 않았습니다.
   이 형태는 페이지에 `barcodeInfo` 블록이 정확히 하나일 때만 인정합니다.
2. `<div class="barcodeInfo">` 영역 안의 `회원번호 : 값`, `회원바코드 : 값`, `바코드번호 : 값`, `바코드 : 값` 문구 (이전 가정. 그대로 지원).
   지원하는 모양은 라벨과 값이 **같은 `<span>` 안**에 있는 형태(`김하나 <span>회원번호 : 값</span>`)와 `<span>` 없이 **일반 글자**로 있는 형태(`김하나 회원번호 : 값`)입니다.
   앞쪽 글자에 라벨이 있고 값이 별도의 직접 자식 `<span>`에 있는 형태(`회원번호 : 값<span>값</span>`, `회원번호<span>값</span>`)는 두 값이 **같아도** 어느 쪽인지 추측하지 않고 거부합니다.
3. `name` 또는 `id`가 `memberNo`, `memberNum`, `memberNumber`, `memberBarcode`, `memberBarcodeNo`, `userBarcode`이고 `value`가 있는 태그
4. `data-member-no`, `data-member-barcode`, `data-user-barcode` 속성

추측하지 않고 실패(본인 확인 불가)로 보는 경우: `barcodeInfo` 안의 `<span>`이 둘 이상(같은 값이어도), 라벨 없는 블록이 둘 이상이거나 다른 `barcodeInfo` 블록과 함께 있음,
`<span>` 뒤에 공백이 아닌 글자가 있음, `<span>` 앞뒤에 다른 요소가 있음, `<span>` 안에 태그가 있음,
앞쪽 글자에 `회원번호`·`바코드` 라벨이 있거나 같은 블록·페이지의 라벨 형태와 라벨 없는 `<span>` 값이 함께 있음(값이 같아도), 값 형식이 이상함, `barcodeInfo`가 중첩되거나 닫히지 않음,
`script`·`template` 등이 닫히지 않음. 위 형태들은 페이지 전체에서 합쳐 보므로 다른 곳의 회원 전용 필드와 값이 다르면 역시 실패입니다.
`barcodeInfo` 밖의 `<span>`, 블록 안의 맨 글자(표시 이름 포함), 주석·`<script>`·`<style>`·`<template>` 안의 표시는 회원번호로 **선택하지 않습니다**.

**숨은 영역: 선택 제외와 충돌 검사는 다릅니다.** `<script>`·`<style>`·`<template>` 안의 내용은 회원번호를 고르는 데는 절대 쓰지 않지만(숨은 영역에만 있으면 "찾지 못함"),
화면에 보이는 회원번호와 충돌하는지는 검사합니다. 목록 행 파서는 이 영역 안의 행도 읽을 수 있으므로, 숨은 영역의 다른 회원 증거를 무시하면 그 행이 본인 것으로 통과할 수 있기 때문입니다.
- 화면 회원번호가 있을 때 숨은 영역에 `barcodeInfo` 블록이 있으면 값이 **같아도** 거부합니다.
- 숨은 영역의 회원 전용 필드·`data-*` 값이 형식 오류이거나 화면 회원번호와 다르면 거부합니다(같은 값은 허용).
- 숨은 영역 안의 `barcodeInfo`가 닫히지 않았거나, 숨은 영역 안에 또 `script`·`style`·`template` 태그가 있으면(중첩·이상한 모양) 거부합니다.
- 주석(`<!-- -->`)은 기존대로 검사하지 않고 무시합니다.

로그인 아이디 hidden 값(`userId`), 메인 화면 SSO 폼의 `id`·`name` 값, 책 식별자(`bookKey`, `regNo` 등), 바코드 이미지 주소, 회원 이름은 회원번호로 쓰지 않습니다.
화면이 이 중 어느 것과도 맞지 않으면 "화면에서 회원번호를 찾지 못했습니다"가 뜹니다. 이름 대조로 되돌리지 않습니다.

**회원 이름(선택 항목)**: 관측된 형태의 `<span>` 앞 표시 이름 글자를 읽어, `songpa-accounts`에 회원 이름을 넣어 두었다면 함께 대조합니다
(다르면 실패). 이름은 보조 확인일 뿐 신원이 아니며, 넣지 않아도 회원번호 확인은 그대로 합니다. 표시 이름 없이 `<span>`만 있는 화면에서 회원 이름을 넣어 두면
"회원 이름을 확인할 수 없습니다"로 실패합니다.

### 메인 화면의 전자책 SSO 폼 (좁은 예외)

로그인된 메인 화면에는 전자책 사이트로 넘어가는 폼이 하나 있습니다: `name="ebookForm"`, `method="post"`,
`action="https://ebook.splib.or.kr/login_sso.asp"`, 비밀번호 없이 hidden `id`·`name` 두 칸만 있음.
주소에 `login`이 있어 일반 "로그인 화면" 검사가 로그인된 메인 화면을 잘못 거부했습니다. 이 스크립트는 이 폼을 **제출하지 않습니다**.

- 예외는 **메인 화면(`/intro/index.do`)에서만** 씁니다. 목록 화면·로그인 응답에서는 같은 폼이 있어도 로그인 화면으로 봅니다.
- SSO처럼 보이는 폼이 **정확히 하나**이고, 이름·method·주소가 정확히 같고(쿼리·조각·다른 호스트·다른 경로 불가),
  안쪽이 값이 있는 hidden `id`·`name` 두 칸뿐일 때만 그 폼 하나를 빼고, 나머지 페이지에는 **기존 일반 로그인 화면 검사를 그대로** 합니다.
- 두 개 이상, 주소·method·이름 변경, 비밀번호·버튼·다른 입력이 붙은 경우, 또는 다른 곳에 일반 로그인 폼·비밀번호 칸이 있으면 그대로 로그인 화면으로 거부합니다.
- 태그 안 줄바꿈·공백, 대문자 속성 이름·값(`METHOD="POST"`), `id`·`target` 같은 추가 속성은 그대로 허용합니다. 속성 값 안에 `>`가 있으면 모양이 맞지 않아 거부합니다.
- 폼의 값은 모양 확인에만 쓰고 저장·표시·비교하지 않습니다.

### 서버 주체 증명 (회원정보 확인 화면)

정확한 상수 주소 `https://splib.or.kr/intro/menu/10101/program/30045/memberModifyPwCheck.do` 하나만 씁니다.

- 방금 로그인해서 받은 JSESSIONID를 `Cookie`로 고정해 **GET**만 합니다. 주소·본문에 아이디를 넣지 않고, 이 화면의 비밀번호 확인 폼은 **제출하지 않으며**
  비밀번호 칸의 값은 읽지 않습니다. 리다이렉트는 따라가지 않습니다.
- 전용 응답 검사: HTTP 200만, 응답 주소가 위 주소와 **문자 그대로** 같아야 함(쿼리·`?`·조각·`;jsessionid`·끝 `/`·다른 출처·`http` 불가),
  JSESSIONID 변경·삭제 없음, `action`에 `login`이 있는 일반 로그인 폼 없음.
  이 화면에는 원래 비밀번호 칸이 있으므로 **이 화면에서만** 비밀번호 칸을 로그인 화면 증거로 보지 않습니다. 다른 화면의 일반 로그인 화면 검사는 그대로입니다(전역 예외 없음).
- 주체로 인정하는 모양: 실제로 그려지는 영역의 `<input>` **하나**, `type="hidden"`, `id="userId"` **그리고** `name="userId"`(대소문자 정확히), 속성 중복 없음,
  `disabled`·`form` 속성 없음, 비어 있지 않은 `value`. 값은 HTML 엔티티만 풀고 앞뒤 공백·대소문자를 고치지 않고 저장한 아이디와 **정확히** 비교합니다.
- 거부: 없음, 빈 값, 둘 이상(같은 값이어도), `userid`/`loginId` 같은 다른 아이디 필드가 함께 있음, hidden이 아님, id·name 중 하나만 있음, 속성 문법 오류,
  `<input>`이 아닌 요소, 주석·`script`·`style`·`template`·`textarea`·`noscript` 등 숨은 영역에만 있음, 숨은 영역에 **다른** 아이디가 반사되어 있음, 닫히지 않은 숨은 영역.
- 폼 안에 들어 있는지는 관측하지 않았으므로 검사하지 않습니다(관측된 화면: 이 hidden 칸 하나, `barcodeInfo` 하나, 비밀번호 칸).
- 같은 응답의 회원번호는 기존 `parseIdentity`로 읽어 **하나로 확정**되어야 합니다. 증명에 실패해도 그 응답에서 관측된 회원번호는 계정 간 충돌 검사에만 쓰고 저장하지 않습니다.
- 회원번호 기록이 있어도 매 조회마다 이 증명을 다시 합니다. 기록은 직접 입력 회원번호를 건너뛰는 지름길이 아닙니다.

### 확인된 회원번호 기록과 저장 규칙

- 키: `SPLIB_VERIFIED_MEMBERS_V1`. 형식 `{"version":1,"records":[{"origin":"https://splib.or.kr","loginId":"…","memberId":"…"}]}`.
  공식 출처 + 로그인 아이디 하나에 회원번호 하나. 형식이 다르거나, 같은 아이디·같은 회원번호가 두 번 있으면 기록 전체를 믿지 않습니다
  (회원번호 없는 계정은 조회하지 않고, 기록도 쓰지 않음. 직접 입력한 회원번호가 있는 계정은 계속 조회).
- 저장은 모든 계정의 마지막 증명과 계정 간 충돌 검사(같은 회원번호·같은 세션)가 끝난 뒤, **숨겨지지 않은 성공 계정의 첫 확인값만** 한꺼번에 합니다.
  실패·바뀜·모호·세션 교체·충돌로 숨겨진 계정은 저장하지 않습니다. 앞서 성공한 계정도 뒤 계정과 충돌하면 저장하지 않습니다.
- 저장 직전에 잠금 안에서: 계정 목록을 다시 읽어 그 계정이 **같은 아이디 하나·같은 비밀번호로 그대로 있는지** 확인(바뀌었으면 저장하지 않음),
  기록을 다시 읽어 검사, 같은 값이 이미 있으면 그대로(다시 쓰지 않음), **다른 값이 이미 있거나 그 사이 다른 회원번호가 직접 입력되었거나 같은 회원번호가 다른 아이디에 있으면
  절대 덮어쓰지 않고** 그 계정 결과를 숨깁니다. 이 경우 묶음 전체를 쓰지 않습니다(전부 아니면 전무). 최신 기록에 병합하므로 다른 실행이 쓴 기록도 그대로 남습니다.
  병합 결과는 `Keychain.set` 한 번으로 쓰고 다시 읽어 같은지 확인합니다. 잠금 안에서는 `await`·네트워크를 쓰지 않습니다.
- 저장하지 못하면(잠금 사용 중·잠금 불가·쓰기/확인 실패·기록 손상) 이번 결과는 보여 주되 "확인한 회원번호는 저장하지 못했습니다" 안내를 붙이고, 저장 성공으로 표시하지 않습니다. 다음 조회에서 다시 증명합니다.
- 메인 스크립트는 계정 목록(`SPLIB_ACCOUNTS`)과 비밀번호를 **절대 쓰지 않습니다**. 그래서 예전 설정 스크립트가 계정 목록을 저장해도 필드를 잃지 않습니다.
  설정 스크립트에서 계정을 지워도 확인 기록은 남습니다(같은 아이디를 다시 추가하면 그 기록과 대조).

**배타 잠금 (가정 포함)**: 기록을 쓰는 실행은 `FileManager.local()`의 Library 폴더에 무작위 이름의 자기 claim 파일을 만든 뒤
`FileManager.copy(claim, songpa-verified-members.lock)`으로 잠금 파일을 만듭니다. [Scriptable 공식 문서](https://docs.scriptable.app/filemanager/#-copy)에 따르면 `copy`는 **대상 파일이 이미 있으면 실패**합니다
(`writeString`·`move`는 덮어씀). 복사가 성공했고 잠금 파일 내용이 자기 claim과 같을 때만 진행합니다. 실패하면 저장하지 않습니다.
시간이 지났다고 남의 잠금을 지우지 않습니다(살아 있는 다른 실행의 잠금을 지우는 ABA 문제 방지). 끝나면 자기 claim·자기 잠금만 지웁니다.
조회 실행 표시(lease)는 확인·쓰기 사이 틈이 있는 권고용이라 이 저장의 정확성 근거로 쓰지 않습니다.
**실제 iPhone/Mac Scriptable에서 `copy`가 이 경우 원자적으로 실패하는지는 확인하지 못했습니다**(Node 모의 객체로만 시험). 키체인 비교 후 교체(compare-and-swap) 같은 기능은 쓰지 않았습니다(Scriptable에 없음).
저장 도중 앱이 강제 종료되어 잠금 파일이 남으면 이후 첫 저장은 계속 "저장하지 못함"이 됩니다(조회 결과는 계속 보임). 직접 입력한 회원번호로 대신할 수 있습니다.

### 본인 확인 진단 (선택, 사용자가 나중에 직접 실행)

`songpa-identity-check.js`는 메인 스크립트와 같은 코드에서 끝의 진입점만 진단용으로 바꾼 생성본입니다(`importModule`·별도 주소 불러오기 없음).

1. 저장소에서 `node scripts/build-scriptable-identity-check.mjs` 실행 → `scriptable/songpa-identity-check.js` 생성(`--check`로 최신 여부만 확인).
2. 운영 중인 기존 스크립트(iCloud의 메인·설정 스크립트)는 **그대로 둡니다**. 시험하려는 새 메인 스크립트와 진단 스크립트는 Scriptable에 **새 이름**으로 붙여 넣습니다.
3. 진단 스크립트를 실행 → **본인 계정 하나**를 고르고, "로그인 1회 시작"에 동의할 때만 일반 로그인을 한 번 합니다. 취소하면 네트워크 요청이 없습니다.
4. 진단은 회원정보 확인 화면 → 메인 화면 → 회원정보 확인 화면 재증명만 합니다. 대출·상호대차 목록, 업데이트 확인, 회원번호 기록 저장, 계정 목록 수정은 하지 않습니다
   (조회 실행 표시 lease 파일만 잠시 만들고 지웁니다).
5. 결과 창에는 `result: PASS` 같은 코드와 `true/false/null`만 나옵니다. 이 표시만 알려 주세요. 아이디·회원번호·비밀번호·쿠키·화면 원문은 보내지 마세요.

결과 코드: `PASS`, `CANCELLED`, `NO_ACCOUNTS`, `BUSY`, `FAIL_SETUP`, `FAIL_LOGIN`, `FAIL_NETWORK`, `FAIL_PROFILE_RESPONSE`, `FAIL_SESSION_CHANGED`,
`FAIL_PRINCIPAL_MISSING`, `FAIL_PRINCIPAL_AMBIGUOUS`, `FAIL_PRINCIPAL_MISMATCH`, `FAIL_MEMBER`, `FAIL_PROFILE_PARSE`, `FAIL_NAME_MISMATCH`, `FAIL_STORED_MEMBER`, `FAIL_HOME`, `FAIL_FINAL`.

## 목록 읽기

- 대출·상호대차 목록은 로그인·회원번호가 확인된 **빈 페이지 또는 모든 이동 링크를 해석할 수 있는 명시적 마지막 페이지**까지 읽습니다 (최대 30페이지, 위젯 25초·앱 210초 제한).
  한 페이지 건수가 적다고 끝으로 보지 않습니다(서버 페이지 크기를 확인하지 못했기 때문). 그래서 21권이면 4페이지, 20권이면 3페이지(빈 페이지)까지 요청합니다.
- **재확인**: 책이 있는 목록은 빈 끝 페이지까지 읽은 뒤, 같은 페이지들(빈 끝 페이지 포함)을 같은 세션·같은 확인 절차(쿠키·주소·회원번호·시간 제한)로 한 번 더 읽어
  행 지문(식별번호·제목·날짜·도서관·상태)이 첫 조회와 같은지 비교합니다. 재확인한 기록은 다시 더하지 않습니다.
  조회 중 앞 페이지의 책이 반납·삭제되면 뒤 책이 앞으로 밀려 중복 없이 빠질 수 있기 때문입니다. 내용이 바뀌었거나 재확인 중 일반 오류·시간 초과가 나면
  첫 조회 결과는 남기고 "일부만 확인"으로 표시합니다. 재확인 중 세션·인증·신원 문제는 첫 조회와 같이 계정 결과를 모두 숨깁니다.
  처음부터 빈 목록이면 한 번의 확인으로 0권이고, 첫 조회가 이미 일부 확인(오류·최대 페이지 등)이면 재확인하지 않습니다.
  두 번 같게 읽혀도 서버 시점의 일관된 스냅숏을 보장하지는 않습니다(두 조회 사이에 바뀌었다가 되돌아간 경우 등). 확인 가능한 변경을 줄일 뿐입니다.
- **위젯 시간 예산 절충**: 재확인 때문에 목록 요청이 약 두 배가 됩니다(21권이면 대출 목록 8요청). 위젯 예산(25초)은 늘리지 않았으므로
  느린 네트워크나 계정·페이지가 많을 때 위젯에서 재확인이 시간 안에 끝나지 못해 "일부만 확인"이 더 자주 보일 수 있습니다. 앱에서 실행하면 210초 예산을 계정별로 나눕니다. 대출·상호대차 조회 뒤 최종 본인검증 시간도 남깁니다.
- 목록 행은 `<div class="myArticle-list">`와 `<li class="myArticle-list">`를 모두 읽습니다.
  제목이 없는 행은 지난 이력 상태(완료·복귀중·신청취소)일 때만 건너뛰고, 진행 중이거나 상태를 모르면 형식 오류(일부 확인)입니다.
- 상호대차 상태 칸 끝의 `신청취소` 버튼 문구(`요청중신청취소`, `요청중 <a>신청취소</a>`)만 떼어 냅니다. 정확히 `신청취소`는 지난 이력, `입수취소` 같은 문구는 모르는 상태입니다.
- 각 페이지마다 상태 코드, 최종 주소, 로그인 화면 여부, 행 형식을 확인합니다.
- 빈 목록은 그 목록 페이지 주소(`loanStatusList.do` / `dooraeLillStatusList.do`)와 빈 목록 표시
  (`class="noData"`/`no-data` 또는 "자료가/내역이/도서가 없습니다" 문구)가 함께 있을 때만 "0권"으로 봅니다. 이 표시 역시 **가정**입니다.
  빈 목록 표시는 인식한 목록 영역(`<div class="myArticleWrap">` 또는 `<div class="list">`) **안에** 있어야 합니다.
  옆 영역의 `noData`만 있고 실제 목록 구조를 알아보지 못하면 0권이 아니라 형식 오류(일부 확인)입니다.
  알아볼 수 없는 화면은 0권이 아니라 오류/일부 확인으로 표시합니다.
- 뒤쪽 페이지에서 일반 오류(HTTP 500, 형식 오류, 같은 페이지 반복, 최대 페이지·시간 초과, 재확인 불일치)가 나면 그 전까지 확인한 책은 남기고 "일부만 확인"으로 표시합니다.
  로그인·세션·신원 문제가 생기면 이미 읽은 것까지 모두 버립니다.
- 요청마다 제한 시간을 남은 예산 이하로 줄입니다(최소 1초라 예산을 1초 남짓 넘길 수 있음). 예산이 끝나면 새 목록 요청은 시작하지 않고,
  결과 확인용 마지막 회원번호 재확인만 합니다.
- 반납예정일이 달력에 없는 날짜(예: 2.30)면 다음 달로 넘기지 않고 형식 오류(일부 확인)로 봅니다.
- 서버가 마지막 페이지 다음 번호에 빈 페이지 대신 마지막 페이지를 다시 보여 주면 끝을 증명할 수 없어 "앞 페이지와 같음"으로 **일부 확인**이 됩니다(권수와 무관).
  실제 사이트가 이렇게 동작하는지는 확인하지 못했습니다. 보수적으로 둔 것이며, 그런 경우 모든 조회가 "일부만 확인"으로 보일 수 있습니다.

## 같은 책 판단

- 등록번호는 도서관마다 따로 매기는 번호로 봅니다. 그래서 **소장 도서관 + 등록번호**로만 비교합니다.
  - 대출 행: 행에 적힌 도서관(첫 `<strong>`, 속성·안쪽 태그 허용)을 범위로 씁니다. 단 책솔이 대출 행의 도서관은 수령 도서관일 수 있어 등록번호 비교에 쓰지 않습니다.
    도서관을 읽지 못한 행은 대출번호·등록번호로 합치지 않고 모두 보여 주며 "일부만 확인"입니다.
  - 상호대차 행: `제공도서관`만 범위로 씁니다. 수령 도서관으로 소장처를 추정하지 않습니다.
    신청번호는 제공·수령 도서관을 모두 읽었을 때만 비교합니다. 하나라도 없으면 합치지 않고 "일부만 확인"입니다.
- 대출 중복은 같은 도서관 범위의 대출번호(`loanKey` 등)가 같고 내용(제목·반납일·등록번호)도 같을 때만 한 번으로 셉니다.
  같은 대출번호인데 내용이 다르거나, 같은 도서관·등록번호에 대출이 여러 건이면 합치지 않고 모두 보여 주며 "일부만 확인"으로 표시합니다.
  서로 다른 도서관의 같은 등록번호는 다른 책입니다.
- 상호대차와 대출은 **같은 소장 도서관·등록번호의 진행 중 기록이 양쪽에 딱 한 건씩일 때만** 연결합니다.
  여러 건이면 연결하지 않고 따로 보여 주며 경고합니다. 지난 이력(완료·복귀중 등)으로 반납처를 바꾸지 않습니다.
  등록번호가 같아도 제목이 다르면 연결하지 않고(대출 행의 도서관 유지) "일부만 확인"으로 경고합니다. 제목만으로는 연결하지 않습니다.
  수령도서관이 없는 진행 중 상호대차는 연결하지 않고 따로 보여 줍니다.
  제목만으로 원본 기록을 삭제하거나 확정 연결하지 않습니다. 화면에서는 아래 v1.2.6 표시 정책을 적용합니다.
- 식별번호가 없어 중복인지 알 수 없는 대출·상호대차 항목은 모두 남기고 경고합니다. 식별번호의 실제 화면 구조도 확인하지 못한 **가정**입니다.
- 상호대차의 `제공도서관 : 값`/`수령도서관 : 값`은 값이 라벨 `<span>` 안에 있는 형태와 `</span>` 뒤에 있는 형태를 모두 읽습니다.
  진행 중인 상호대차에 수령도서관이 없으면 "수령도서관 미확인"으로 보여 주고 경고합니다.

### 데이터 품질 경고는 "일부만 확인"

모르는 상호대차 상태(표시하지 않음), 풀리지 않은 중복·충돌·연결, 빠진 수령도서관, 형식이 이상한 식별번호가 있으면
목록을 끝까지 읽었더라도 그 계정은 "일부만 확인"입니다. 이 경우 "✓ 조회 완료"나 "0권"으로 확정하지 않고, 위젯과 전체 화면에 경고를 보여 줍니다.
같은 식별번호의 완전히 같은 기록이 두 번 보이면 한 번만 세지만, 조회 중 목록이 밀려 빠진 항목이 있을 수 있다는 증거이므로 "일부만 확인"입니다.

## 화면 표시

- 위젯: 모든 계정 실패는 "⚠️ 조회 실패", 일부 실패는 "⚠️ 일부만 확인", 모두 확인했고 책이 없으면 "✓ 조회 완료"로 구분합니다.
  실패한 계정은 계정 이름 전체와 이유를 한 줄씩 보여 줍니다.
- 전체 화면: 실패 계정은 "조회 실패", 일부만 확인된 계정은 `N권+`와 경고 상자로 표시합니다. 경고·오류 문구는 이스케이프합니다.

## 실행 겹침

위젯 새로고침과 앱 실행이 겹치면 Scriptable 공용 쿠키 저장소 때문에 세션이 섞일 수 있습니다.
메인 스크립트는 이 기기 로컬 파일(`FileManager.local()`의 Library 폴더)에 270초짜리 실행 표시(lease)를 두고,
다른 실행이 표시를 갖고 있으면 이번 조회를 건너뜁니다. 끝나면(실패해도) 자기 표시만 지웁니다.
단, **직접 연 앱은 위젯이 남긴 표시를 넘겨받아 바로 조회합니다** (v1.2.10~). 위젯(25초 예산)이 iOS에 종료되면 표시가 남아
앱이 최대 270초 동안 막혔기 때문입니다. 표시를 넘겨받긴 위젯은 다음 계정 로그인 전에 멈추고 결과를 버립니다.
앱이 남긴 표시, 종류를 알 수 없는 표시, 위젯끼리는 기존처럼 존중합니다.
이 표시는 **원자적 잠금이 아니며** 두 실행이 동시에 통과할 수도 있습니다. 결과가 맞는지는 쿠키 고정과 회원번호 확인으로 지킵니다.
조회가 끝난 뒤 화면에 보여 주기 전에 표시가 아직 자기 것인지 다시 읽어 보고, 다른 실행이 가져갔으면(파일로 관측될 때만) 이번 결과를 버립니다.
이 확인과 실제 표시 사이에도 틈이 있으므로 보장이 아니라 보조 수단입니다.
키체인은 잠금 용도로 쓰지 않습니다.

## 검증 범위와 남은 확인

- Node 합성 테스트 163개와 Mac Scriptable의 실제 조회·초기 대기·순차 갱신·완료 화면을 확인했습니다. 같은 제목의 대출·도착 이력에서 픽업 행동 표시가 사라지고, 대출이 없는 픽업은 유지되는 것을 확인했습니다.

- `FileManager.copy`의 대상 파일 존재 시 실패 계약은 모의 객체로 검사했습니다. 실제 기기에서의 원자성은 증명하지 않았습니다.
- 테스트 HTML은 최소 화면 구조를 본뜬 합성 값이며, 실제 응답·계정 정보·도서 목록은 저장소에 포함하지 않습니다.

## 자동 업데이트

메인 스크립트는 실행할 때 이 저장소의 `scriptable/songpa-loan-tracker.js`에서 `SCRIPT_VERSION`을 확인합니다.
더 높은 버전이 있으면 앱에서는 "지금 업데이트" 창이, 위젯에서는 아래쪽에 업데이트 안내가 뜹니다.
업데이트하면 내 스크립트 파일이 새 버전으로 덮어써집니다. 키체인의 계정 정보는 그대로 남습니다.

배포하는 쪽은 코드를 고친 뒤 `SCRIPT_VERSION`을 올려서 `main`에 반영하면 됩니다.
버전을 올리지 않은 변경은 사용자에게 안내되지 않습니다.

공개용 메인·생성 진단본은 `NATIVE_TRACE = false`가 기본이며 단계·조회 추적 파일을 기록하지 않습니다. 문제를 조사할 때만 기존 상수를 명시적으로 `true`로 바꿀 수 있습니다. 활성화해도 기록 대상은 고정 단계 코드·시간·개수·참/거짓이며 아이디·회원번호·비밀번호·쿠키·도서명은 포함하지 않습니다. 생성본은 메인 변경 후 `node scripts/build-scriptable-identity-check.mjs`로 다시 만듭니다.

## v1.2.6 화면 표시 (title-display-3)

- 한 계정 안에서 전체 제목(공백 정리·NFC만, 권차·부제·문장부호는 그대로)이 같은 대출과 진행 중 상호대차 기록은 화면에서 한 항목으로 보이고, 원래 기록의 반납일·도서관 정보를 유지한다. 기록·개수·상태는 바꾸지 않으며 같은 실물 책이라는 판단이 아니다. 다른 계정끼리, 빈 제목, 같은 종류(대출끼리·상호대차끼리)만 같은 제목인 기록은 묶지 않는다.
- 탭·카드·머리말·위젯의 수는 화면 항목 수(건)이다. 기록 수가 다르면 "기록 N건"을 함께 적는다.
- 식별번호가 없어서 생기는 중복·연결 미확정 안내는 화면에 띄우지 않는다(내부 warnings에는 남음). 네트워크·로그인·본인 확인·일부 페이지 실패·모르는 상태 같은 실제 문제는 그대로 보인다.
- 요약의 대출·픽업·이동 수는 화면 항목별 대표 상태(대출 → 픽업 → 이동)로 한 번만 센다. 혼합 묶음의 대출·반납일과 중립적인 도착 이력을 표시하며 원시 상태·카운터는 보존한다.
- 같은 제목 묶음에 대출 중인 기록이 있으면 대출·반납일·반납처를 먼저 표시한다. 해당 묶음의 상호대차 도착 기록은 픽업 행동 표시 없이 기본으로 접힌 "이전 상호대차 기록"으로 보존하며 위젯에서도 픽업 태그·옛 수령처를 제외한다. 대출이 없는 픽업과 다른 계정의 픽업은 그대로 안내한다.


## v1.2.7 책솔이 반납 위치 표시

- 같은 계정의 같은 전체 제목에 대출이 하나이고 입수·완료 수령 기록의 수령/제공 도서관 쌍이 일치하면, 그 수령처를 표시용 반납처로 사용한다. 원시 대출·상호대차 기록과 `lib`, `provLib`, `shortLib`, `libSummary`, 상태·개수는 바꾸지 않는다.
- 여러 대출·수령처 충돌·필드 누락·식별자/서지 충돌이 있으면 반납처를 미확인으로 표시하고 원래 값은 "대출목록 도서관"으로 구분한다. 소장처를 반납처로 추정하지 않는다. 일반 대출에 남은 옛 상호대차 이력과 다른 계정의 기록은 적용하지 않는다.
- 상세·위젯·도서관별 요약은 같은 표시 위치를 사용한다. 기존 대출 우선·픽업 오표시 제거와 Keychain 저장 규칙은 유지한다. iOS 실기 검증은 별도다.
